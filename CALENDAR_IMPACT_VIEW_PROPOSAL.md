## Where this starts today

`calendar.ts` exports a `CalEvent` type — `date`, optional `time`, `title`,
`short`, `kind: "rates"|"inflation"|"oil"|"mag7"`, `hits` (a flat display
string like `"NQ, Gold, DXY"`), `context`, `history` — and ~50 hand-authored
events. `calendar.tsx` renders a month grid; clicking a day opens a
`DateSheet` modal that prints that day's events as plain text (kind badge,
time, title, `hits`, `context`, `history`). That modal is exactly the "text
modal" the founder wants to evolve — the data already answers WHAT and part
of WHY; nothing today visualizes *which instruments* and *how strongly*, or
surfaces NEXT beyond a separate upcoming-events table lower on the page.

---

## 1. Interaction flow

Keep the entry point identical (day cell → click → sheet opens) so no
navigation behavior changes. Inside the existing `DateSheet`, when a day has
one or more events, each event row becomes expandable into an **impact
view** instead of only printing text:

- **Focal node**: the event itself (title, kind badge, time) — same
  information shown today, just promoted to a visual anchor instead of a
  text line.
- **WHAT**: title + time (already have this).
- **WHY**: the event's `context`/`history` prose (already have this) *plus*
  a row of instrument "spokes" radiating from the focal node — one per
  instrument the event actually touches. Clicking a spoke surfaces that
  instrument's existing `BOOKS` prose (`bias`/`note` from `markets.ts`) as
  the mechanism — "why this event moves this instrument" — instead of
  duplicating new copy.
- **NEXT**: a link to that instrument's book page (`/nq`, `/gold`, …, which
  already renders levels + live chart), and the existing `nextEvent`/
  `upcomingFrom` helpers surfaced as "next print of this kind" — both
  already exist, just relocated into the expanded view instead of only the
  separate upcoming table.

No new route, no new modal system — this extends the `DateSheet` that
already exists. Collapsed state stays exactly as today for anyone who
doesn't expand an event, so this is additive, not a redesign of the
calendar page.

---

## 2. Data model

The founder's constraint — must generalize past CPI/NQ and must reuse the
audited `instrument_influence` model rather than inventing a parallel one —
shapes this directly:

- **Minimal, mechanical addition to `CalEvent`**: `instruments: string[]`
  (slugs matching `BOOKS`/`PIN_CATALOG`, e.g. `["nq", "gold", "dxy"]`),
  populated once per event from the `hits` text that already exists for
  every event. This replaces parsing a free-text string at render time with
  a real array the UI can iterate generically over any `kind`, not just
  rates/inflation.
- **Long-term home for the "why" edges**: `ENGINEERING_AUDIT_001.md` §E's
  `instrument`/`instrument_influence`/`instrument_source` tables — not a
  new schema. An event's `kind` (`rates`/`inflation`/`oil`/`mag7`) is
  already the same vocabulary as the drivers described in `markets.ts`'s
  `BOOKS` prose (rates → DXY/10Y, oil → EIA/OPEC, etc.), so once §E lands,
  the impact view's spokes can be generated by querying
  `instrument_influence` for each `instruments[]` entry instead of only
  showing the flat tag list. That is a drop-in upgrade to the same UI, not
  a rebuild — the component reads "instrument + why" from wherever that
  currently lives.
- Nothing about this event-side change requires Phase 0 (auth) — calendar
  data is public/anonymous today and stays that way.

---

## 3. Buildable now vs. needs new sources

**Buildable now, from data already in the repo:**
- `instruments: string[]` backfill on all ~50 `EVENTS` rows — a data-entry
  pass over the `hits` text that already exists per event, same category of
  work as §E's own seed step, not new research.
- The expand/spoke UI reading `instruments[]` + existing `BOOKS` prose for
  "why" + existing `nextEvent`/`upcomingFrom` for "next."
- Everything renders from data already shipped in this repo — no new
  network calls, no new upstream dependency, no cost impact.

**Needs new data or infrastructure (not in this proposal's scope):**
- A true weighted, multi-hop influence graph (event → catalyst → sector →
  instrument, with `weight`/`relationship` per §E) requires the
  `instrument_influence`/`instrument_source` tables to actually exist and
  be seeded — that's Phase 1 of the already-approved-pending audit, not new
  work invented for this feature. Until that lands, the prototype's "why"
  is a direct one-hop tag (event → instruments named in `hits`), which is
  honest and sourced (it's literally today's `hits`/`context` content,
  just visualized) — not a fabricated correlation.
- A live/real-time economic calendar feed (vs. the current hand-curated
  `EVENTS[]`) is a separate, already-logged gap (`ENGINEERING_AUDIT_001.md`
  §9) — unrelated to whether the impact view itself works.

## 4. Smallest useful prototype

Scoped to be safely isolated and reversible:

1. Add `instruments?: string[]` to the `CalEvent` type (optional, so it
   doesn't break existing events if left unset) and backfill it for the
   ~50 events, derived directly from each event's existing `hits` text.
2. New, self-contained component (e.g. `event-impact-view.tsx`), rendered
   only inside `DateSheet` when an event row is expanded — a plain
   hub-and-spoke layout: the event as a centered card, instrument chips
   arranged around/below it, each chip linking to its book page and, on
   click, surfacing that instrument's `bias`/`note` text inline.
3. Build with existing primitives only — flex/grid layout, the app's
   existing pill/card CSS, maybe simple CSS connector lines — **no new
   charting/graph-visualization library**, and no SVG animation pass yet.
   This validates the interaction and data shape cheaply before any
   investment in the animated flow-diagram look from the founder's visual
   reference.
4. Zero changes to the month grid, upcoming-events table, `AskTape`
   integration, or any other route.

This is small enough to build, screenshot, and get sign-off on before any
further investment — consistent with "avoid a broad rewrite."

---

## 5. Engineering complexity / performance risks

- **Low risk as scoped above**: no new server calls, no new dependencies,
  no schema/migration work, no auth dependency. Everything renders from
  data already resident in the client bundle (`calendar.ts` + `markets.ts`)
  the same way the page does today.
- **Where risk actually lives — flagging so scope doesn't creep silently**:
  1. A genuine animated flow-diagram (colored lines drifting between nodes,
     per the founder's earlier visual reference) is real design + engineering
     work — a layout algorithm for a variable number of instruments per
     event, SVG path animation, and mobile-width constraints for a
     multi-node diagram. That should be scoped as its own follow-up once
     the data/interaction model above is validated, not built speculatively
     now.
  2. Wiring the *weighted* `instrument_influence` graph (rather than the
     flat `instruments[]` tag list) depends on Phase 1 of
     `ENGINEERING_AUDIT_001.md` (the DB migrations) actually being
     approved and seeded — that's a prerequisite outside this feature's own
     scope, not something to pull forward just for the calendar.
  3. Generalization discipline: because `instruments[]` and `kind` are
     already generic across all ~50 events (not special-cased fields), this
     naturally covers every `CalKind`, not just CPI/NFP — no per-event
     branching logic needed in the component itself.

## Recommendation

Approve steps 1–4 above as the prototype (mechanical data backfill + one
new isolated component inside the existing modal). Hold the animated
flow-diagram visual treatment and the full `instrument_influence` DB wiring
as explicit follow-ups, sequenced after Phase 1 of the standing engineering
audit — not bundled into this pass.

**The honest constraint that shapes everything here**: ACTA has zero social-listening or sentiment infrastructure today, paid or free — only RSS news wires (`desk.ts`) and plain search-URL links. Any "crowd context" that isn't a fabricated number has to be built from that, or it's not real. That's what the proposal below does.

**Smallest useful prototype — "Wire Attention," not a sentiment score:**
- **What it shows**: for whatever event/node is currently focused, a plain count — *"N mentions across M distinct outlets in the last 24h"* — plus the list of contributing outlets. That's it. No polarity, no bullish/bearish, no confidence number.
- **Where the data comes from — 100% already live, zero new vendor**: `getNameNews({ q })`, the same server function `BookNews`/`market-view.tsx` already call per instrument today. This prototype would call it with the focused event/node's label as the query and count + de-duplicate-by-source the real results — not a new integration, a new *use* of one that already exists.
- **Which "crowd context" dimensions this honestly covers**: *attention concentration* (mention count) and *source diversity/provenance* (the outlet list itself, already carrying each item's real source). It does **not** attempt *narrative acceleration*, *disagreement vs. consensus*, or *divergence between price and crowd attention* — those need either stored time-series history (to know what "normal" volume looks like) or real NLP clustering across headlines, neither of which exists; faking a trend line or a consensus score from a single point-in-time count would be exactly the "gamified score" the guardrails rule out.
- **Guardrail-by-guardrail**:
  - *Not investment advice / not predictive* — a raw count with no direction or forecast language.
  - *Measured vs. AI interpretation, clearly distinguished* — the count itself is measured (server-side, deterministic). An optional one-line AI gloss ("what these headlines have in common") would be a **separate, clearly-labeled `askTape` call** — flagging this explicitly because it's the one piece here that is *not* free: it would consume the existing rate-limited xAI budget, so it needs an explicit yes/no before being added, not an assumption.
  - *Attribution/provenance preserved* — every count is backed by real, visible source names, same as `BookNews` already does.
  - *No gamified score* — deliberately a plain count, not an index.
  - *Utility-first, second-monitor friendly* — fits directly into the existing Watch Mode "Human Signal" block as a factual line above the existing search links, not a new module.
- **What this needs before even the smallest version can be built** (so nothing is assumed settled): (1) a yes/no on whether the AI-gloss line ships at all, given it's the one part with a real recurring cost; (2) a decision on time window (24h is proposed, arbitrary); (3) explicit sign-off that "count + source list, no score" is the right ceiling for a v1, since the more interesting dimensions (acceleration, divergence, consensus) all require infrastructure ACTA doesn't have yet and are out of scope until that's built or explicitly funded.

## Product Discovery — Do Not Block Launch (research complete, no code changed)
- [x] Evaluate optional user-connected personal AI/provider choice — analysis below.

**Value**: today ACTA pays 100% of AI cost per `askTape` call from its own `XAI_API_KEY` (rate-limited, but still ACTA's spend). Letting a user bring their own key inverts that: power users get to use a provider/model they already pay for and trust, and ACTA's own recurring AI cost stops scaling with usage — directly serves the "extremely lean recurring cost" constraint in `OPS_DIRECTIVE_001.md`.

**Auth/privacy implications**: a stored API key is a credential to a *third party's* billing account — this needs real per-user accounts (today's auth is off, per `ENGINEERING_AUDIT_001.md` §2) and encryption at rest, not a plain DB column; it must never reach logs/analytics/error reporting. This is meaningfully more security surface than anything ACTA holds today and should not be built before auth is actually turned on for real.

**Provider constraints**: providers don't share one API shape. The good news: xAI's own API (already integrated in `tape.ts`, `https://api.x.ai/v1/chat/completions`) is OpenAI-compatible, so "OpenAI-shaped chat completions" as the first supported shape covers OpenAI *and* xAI *and* most self-hosted/compatible endpoints with one integration, not three. Anthropic's native Messages API is a different shape and would be a second, separate integration — real work, not a config toggle, and worth sequencing after the first shape ships.

**Recurring-cost impact**: net **reduction** in ACTA's own AI spend as adoption grows (usage shifts to the user's own provider bill), at the cost of building and maintaining a second (BYO-key) code path alongside the existing ACTA-hosted one.

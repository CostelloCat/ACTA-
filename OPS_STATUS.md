## ACTA Relationship Engine — preview (2026-09-20)

Built per Ops's "build an ACTA Relationship Engine preview" directive, as a small, isolated prototype — no existing route or component modified.

- **Preview route**: `/lab` (e.g. `<preview-url>/lab`). Not linked from nav or any existing page; reachable only by typing the URL, so it can be reviewed without committing ACTA to the final UX.
- **Files changed**: 3 new files only — `src/lib/impact-map-data.ts` (static demo data), `src/components/impact-map.tsx` (the visualization), `src/routes/lab.tsx` (the page). `src/routeTree.gen.ts` also updated, auto-generated by the router's own build step. - **What it shows**: pick CPI or FOMC + dots, then click through EVENT → MECHANISM → ASSETS → SECTORS → COMPANIES. Clicking any node highlights its connected path and opens a WHAT / WHY / NEXT panel below the diagram (what the node is, why it's connected, and either a link to the matching ACTA book page or the next scheduled print of that kind). The EVENT card's WHAT/WHY text is pulled live from the real `calendar.ts` data, not invented.
- **What's real vs. mocked**: the event itself, its date/time, and its WHAT/WHY context are real, live ACTA calendar data. The mechanism → asset → sector → company relationships and every "why it's connected" line are **hand-curated/illustrative for this demo**, grounded in the same domain knowledge already in `markets.ts`'s `BOOKS` prose (not invented from nothing, not copied from any competitor) — clearly labeled as such in a provenance note under the diagram, per the no-fake-data house rule.
- **What data would be needed for production**: a real, sourced instrument-influence dataset (event-study or correlation-based) instead of static prose — this is exactly the `instrument`/`instrument_influence`/`instrument_source` model already proposed in `ENGINEERING_AUDIT_001.md` §E, not a new schema. Production would also want this wired to every calendar event generically (via a small `CalEvent.instruments[]`-style field) rather than the two hand-picked demo events shown here.
- **Performance/architecture notes**: fully static — no new network calls, no new dependencies, no DB/schema changes. Diagram layout is a fixed-grid SVG computed from percentages (no DOM measurement, no ResizeObserver), so it's cheap and SSR-safe. Verified with `npm run typecheck` and a full `npm run build` (Vercel preset), both clean, plus a local dev-server visual check (tab switching, node selection, edge highlighting, and the "Open ACTA book" link all confirmed working in a headless browser).

## Product Discovery — Do Not Block Launch (research complete, no code changed)
- [x] Evaluate optional user-connected personal AI/provider choice — analysis below.

**Value**: today ACTA pays 100% of AI cost per `askTape` call from its own `XAI_API_KEY` (rate-limited, but still ACTA's spend). Letting a user bring their own key inverts that: power users get to use a provider/model they already pay for and trust, and ACTA's own recurring AI cost stops scaling with usage — directly serves the "extremely lean recurring cost" constraint in `OPS_DIRECTIVE_001.md`.

**Auth/privacy implications**: a stored API key is a credential to a *third party's* billing account — this needs real per-user accounts (today's auth is off, per `ENGINEERING_AUDIT_001.md` §2) and encryption at rest, not a plain DB column; it must never reach logs/analytics/error reporting. This is meaningfully more security surface than anything ACTA holds today and should not be built before auth is actually turned on for real.

**Provider constraints**: providers don't share one API shape. The good news: xAI's own API (already integrated in `tape.ts`, `https://api.x.ai/v1/chat/completions`) is OpenAI-compatible, so "OpenAI-shaped chat completions" as the first supported shape covers OpenAI *and* xAI *and* most self-hosted/compatible endpoints with one integration, not three. Anthropic's native Messages API is a different shape and would be a second, separate integration — real work, not a config toggle, and worth sequencing after the first shape ships.

**Recurring-cost impact**: net **reduction** in ACTA's own AI spend as adoption grows (usage shifts to the user's own provider bill), at the cost of building and maintaining a second (BYO-key) code path alongside the existing ACTA-hosted one.

**Lean architecture recommendation**: (1) sequence this after real accounts exist — a stored key has to be scoped to a signed-in user, so this is downstream of the Desk Profile/auth work already audited, not a parallel track; (2) ship one OpenAI-compatible BYO-key path first (covers OpenAI + xAI + compatible endpoints); (3) keep the current ACTA-hosted `askTape` as the permanent, always-on default — BYO-key is additive, never a wall in front of the free experience, per "ACTA should not force one AI provider" (and per not gating the core product behind user setup).

No code changed for this item — discovery only, per Ops's instruction.
